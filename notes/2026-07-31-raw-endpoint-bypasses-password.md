# 2026-07-31 · raw 直链绕过分享口令，等于商城付费可绕

- **类型**：踩坑排查 / 安全
- **涉及文件**：`worker/src/index.ts`（`/dl/:code/raw`）
- **证据**：commit `1baf916`（12 insertions, 1 deletion）
- **记录于**：2026-10-18（回填，逐条对照当前代码验证）

## 问题

分享链接支持设置口令，正常分享页 `/dl/:code` 会要求输入口令。
但同一个文件还有一个** raw 下载端点 `/dl/:code/raw`** —— 它直接调
`downloadFileStream(...)` 吐文件流，**完全没有校验口令**。

后果不是"多看一个页面"，而是：**任何知道 share code 的人都能直接下载文件本体，
绕过购买验证**。而商城正是靠 TG 分享链接做自动发货的，
所以影响面覆盖所有走这条路的商品，包括已经卖出去的历史商品。

## 权衡

| 修复范围 | 代价 | 选择 |
|---|---|---|
| 只在分享页拦，raw 留给已登录态 | raw 是无状态直链，没有可依赖的登录态，等于没修 | ✗ |
| 给 raw 加同样的口令校验 | 需要口令的调用方要改传 `?password=`；分享页流程不受影响 | ✓ |
| 顺手把 `/img/` 图片直链也锁上 | 会破坏商品预览图展示，而预览图本就是有意公开的 | ✗ 明确排除 |

最终选择最小必要修复：只在 `share.hasPassword` 时要求 `?password=`
通过 `verifySharePassword`，否则 `403`；`/img/` 与正常分享页流程保持不变。

## 结论

`1baf916` 落地后，**2026-10-18 复查确认校验仍在位**，而且这个模式已经扩散 ——
`worker/src/index.ts` 里 `hasPassword` 判断从当初 1 处增长到 **5 处**
（约 1032 / 1063 / 1067 / 1126 / 1139 行），说明后续新增端点有照着补。

**可复用规则**：鉴权是**按端点生效的，不是按资源生效的**。同一个文件只要多一个
出口（raw 直链、缩略图、Range 下载、缩略预览、批量打包），每个出口都要各自鉴权 ——
给"页面"加了口令而漏掉"直链"，是最典型的付费绕过路径。

排查方法：grep 出所有能吐文件流的路由，逐个确认是否落在口令校验之后，
而不是只看主流程有没有校验。
