# 清理 git 历史里的明文登录口令

## 问题

`notes/2026-11-07-manual-cleanup-orphans-frontend-fix.md` 的结论里明文写着登录口令，随提交 `f32b2b3` 进入 main 历史并公开在 GitHub 上。口令本身已在后台轮换，但旧值仍躺在公开历史里，旧克隆或直接用旧 SHA 访问都能看到。

## 权衡

- **只改口令、不清历史**：旧值继续留在历史里，清理不彻底。
- **只清历史、不改口令**：已泄露的口令仍然有效，清理没有意义。
- **改写全部历史（git-filter-repo）**：彻底，但 `f32b2b3` 之后的所有提交 SHA 都会变；旧 PR 分支和已开的 PR 带着旧历史，合并会把口令带回来，必须一并处理；且需要 force-push，会触发一次部署。

## 结论

- 顺序：先轮换口令（用户已做），再改写历史。
- 用 `git-filter-repo --replace-text` 在副本里重写 main 的全部 86 个提交，把口令替换为 `***REMOVED***`；验证：重写后历史中口令出现 0 次，与旧 main 对比仅 1 个文件 1 行变化，口令引入之前的提交 SHA 完全不变，新 main 为 `84288310`。
- 助手侧没有任何可用的 git 推送凭证（连接器也只能做普通提交、不能改写历史），force-push 由用户在自己的 git 客户端里用 bundle 执行；push 触发部署运行 #23，23 秒成功，线上行为不变（内容只改了 1 行）。
- 旧 PR 分支（含旧历史）需删除；PR #6 的分支基于旧 main，作废后在新 main 上重建，见 `notes/2026-11-15-openapi-complete-mount.md` 的重建一节。
- 遗留：旧克隆里仍有旧值，需重新克隆；GitHub 上旧提交用 SHA 直接访问可能还残留一段时间，待 GC。
